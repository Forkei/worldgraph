# Research 12 — What investigation platforms actually give the analyst: object models, control loops, the gap

*Research agent report, 2026-08-30. From vendor docs, the MIRSAP 2005 manual, doctrine PDFs, academic evaluations. Question: what do Palantir / i2 / Maltego / HOLMES / collection management / genealogy software actually do, structurally — and what would the "Tony Stark version" do that none of them do.*

## 1. Palantir Gotham / Foundry
- **Object model**: objects, properties, links + Actions/Functions on datasets ([core concepts](https://www.palantir.com/docs/foundry/ontology/core-concepts/)). Gotham reduces everything to **Entity, Event, Document**; events = object types with start/end for the timeline.
- **Pivoting**: Object Explorer search grouped by type; "search around" by link type with counts and pre-filter; chained search-arounds saveable as templates; "link merging" folds intermediaries into edges. **Saved *exploration* = live query re-evaluated on new data; saved *list* = frozen snapshot** — the single most reusable design idea in the product ([save](https://www.palantir.com/docs/foundry/object-explorer/save-explorations/)).
- **Resolution — the surprise**: Foundry does **not** do fuzzy entity resolution. Multi-Datasource Objects join on a *shared primary key*, column-wise ([MDO](https://www.palantir.com/docs/foundry/object-permissioning/multi-datasource-objects/)). Resolution is pushed into pipelines forward-deployed engineers write.
- **Alerting**: object-set conditions (added/removed/modified/threshold) evaluated "within minutes"; effects = notification/Action/Function; noise controls mute, pause, expiry (≤ 6 months), auto-mute at 80% failure ([Automate](https://www.palantir.com/docs/foundry/automate/overview/)).
- **Provenance**: markings "travel with each unit of data through derivation"; lineage to backing datasets; "checkpoints" demand a justification for sensitive queries (LAPD: ALPR search requires a case number).
- **Verdicts**: "I click on him and a web would spread out" vs. point-based scoring feedback loops (Brayne), NYPD "a cool tool, but that's about it", export fights, 11 NHS trusts suspending. **Structural lesson: superb ontology + pivot + permission substrate with no native notion of a task, a hypothesis, or a gap.**

## 2. IBM i2 Analyst's Notebook / iBase
- **Grammar**: entities, links, attributes; three entity representations — Icon (association chart), **Theme Line** (persistent thing on a timeline), **Event Frame** (dated event pinned to theme lines). Link **multiplicity** is first-class: Single (count rolls up), Multiple (one per occurrence), Directed.
- **Grading lives on the card**: every item carries Grade One/Two/Three, Source Type, Source Reference — the 5x5x5 / **3x5x2** triple attached *per assertion*. Convention: solid = confirmed, dashed = unconfirmed, dotted = tentative; restrict primary analysis to B2+.
- **3x5x2** (UK, 2016→): Source 1 Reliable / 2 Untested / 3 Not reliable × Intelligence A known directly / B known indirectly, corroborated / C known indirectly / D not known / E suspected false × Handling P / C. OSINT typically 2D. **Source reliability and information credibility are orthogonal and attach to each item.**
- Tools: centralities, Find Path, Find Connecting Network, Visual Search (draw a pattern, find matches), conditional formatting; i2 Analyze adds visual queries and alerting.

## 3. Maltego
- Transforms = functions entity → entities; Machines = macros. The Machine language is a tiny **expansion-policy DSL**: `run(..., slider:N)`, `paths{}`, `userFilter()` to pause for manual pruning, filters `type() incoming() degree() age() bookmarked()`, actions `delete() deletebranch() bookmark()`, `onTimer(90)` for perpetual monitoring ([syntax](https://docs.maltego.com/en/support/solutions/articles/15000019254-machine-syntax-reference)).
- **Noise**: "All Transforms" runs everything; the slider caps output but "12 = first 12, not best 12". Pros plan objectives first, use transform sets, collections (auto-collapse ≥ 25 same-type nodes), and "retain only the Entities and Links that are directly relevant to the objective". **Lesson: expansion needs a budget and a relevance filter, and today the human is the filter.**

## 4. Case-management / OSINT workflow tools
- **Hunchly**: every visited page → URL, timestamp, hash, MHTML; tags; "automatic, transparent audit trail". Provenance by default, zero analysis.
- **Bellingcat auto-archiver**: feeders (Google Sheet) → extractors → enrichers (hash, timestamp, WACZ, Wayback) → databases → storages; the **spreadsheet is the queue and the audit log**. Guidance: no fixed pipeline, Berkeley Protocol, peer review.
- **Linkurious**: the cleanest alert→case model — *Alert* has *models* (Cypher patterns); a *target* entity dedupes matches into a *case* (subgraph + computed attributes); statuses Unconfirmed → In progress → Confirmed/Dismissed with notes, assignment ([lexicon](https://doc.linkurious.com/user-manual/latest/alert-lexicon/)).
- **SpiderFoot**: pub/sub module graph — modules declare `watchedEvents` / `producedEvents`; each event carries a hash, `sourceEventHash` (lineage), confidence/visibility/risk 0–100; YAML correlation rules. **The best open-source model of "new fact triggers more collection."**
- **Recon-ng**: modules named `recon/<input table>-<output table>/name` — the schema *is* the pipeline.
- **ICIJ Offshore Leaks**: relationships include `same_name_as`, `same_id_as`, `similar`, `probably_same_officer_as` — **resolution uncertainty encoded as typed edges, not merges** ([FAQ](https://offshoreleaks.icij.org/pages/faq)). Datashare: scan → index → NER; batch search re-runnable after new indexing.

## 5. HOLMES 2 / MIRSAP — a human-run task graph
Born of the Byford finding that "a backlog of unprocessed information led to the failure to connect crucial pieces of related information" (Yorkshire Ripper). Full manual: [MIRSAP 2005](https://library.college.police.uk/docs/APPref/MIRSAP.pdf).
- **Objects**: Documents (Action, Statement, Officer's Report, Interview, Questionnaire, House-to-House, Message, Other), Exhibits, Intelligence. **Indexes**: Nominal (identified / unknown / unidentified, elimination code, suspect marker "only at the direction of the SIO"), Location, Telephone, Vehicle, Category (hierarchical), Organisation, Sequence of Events. **Policy File**: the SIO's numbered, signed decision log. Rule: *"No index record should stand alone and each record should be capable of being traced to its originating document."* Cross-refs index↔index (link word ≤ 10 chars, `X` prefix = past, `?` suffix = suggested, e.g. `OWNER?`), index↔document, document↔document.
- **The loop**: document arrives → *Receiver* reads, sets priority, raises urgent Actions, assesses TIE returns → Registration → Typing → Proofreading → Disclosure → Reading → Indexing → Approval → *Document Reader* underlines what to index and "where any line of enquiry is apparent, give explicit instructions to raise an appropriate Action" → *Indexer* creates/links records and "must interrogate the system… as they link relevant facts" → *Action Manager* "continually researches the Action queues… updates their priorities."
- **Action state machine**: "a written instruction to carry out a task in connection with a particular line of enquiry" — one line of enquiry per Action, originating document cited, duplicate-check before raising. States: For Allocation → Allocated → Completed → Resulted → Filed; side states Referred (agreed not pursued), Pended (re-allocate after date). Priorities High (fast-track) / Medium (main line) / Low ("should not be allocated just as a matter of course"). Reopening a Filed Action requires a *new* Action citing the old one. Review ≥ every 28 days. **Enquiry officers may not self-generate enquiries — they *recommend* on the Action.**
- **TIE (Trace / Interview / Eliminate)**: identify groups that may include the offender; nominals index-linked to every TIE category they fit; elimination codes 1 Forensic · 2 Description · 3 Independent witness · 4 Associate alibi · 5 Spouse alibi · 6 Not eliminated; **"implication and elimination are always provisional."** HOLMES 2 adds a "dynamic reasoning engine to identify new lines of enquiry" and cross-incident matched records with source, date, state.
**The most complete investigation object model in existence — and entirely manual.**

## 6. Collection management (intelligence doctrine)
Requirement hierarchy: CCIR → **PIR** ("Will the adversary attack within 72h?") → **EEI/SIR** ("Has the artillery deployed forward?") → **Indicator** (observable that confirms) → **SOR** (indicator bound to where/when/what, with **LTIOV** — latest time information is of value — back-planned from the decision it serves) → tasked asset, which must "tag all reports with the numbers of the SORs they satisfy" ([FM 34-2](https://www.globalsecurity.org/intell/library/policy/army/fm/34-2/ch3.htm), [JP 2-01](https://www.bits.de/NRANEU/others/jp-doctrine/jp2_01%2812%29.pdf)). Requirement quality: Specific, Measurable ("possible to determine when a requirement has been filled"), Realistic, Timely.
- **Tables**: requirements register; collection plan worksheet (PIR | Indications | Specific information | Assets | Place/time to report); synchronisation matrix; asset evaluation; dissemination journal (which messages satisfied which SOR). Police version must record "when sources have been contacted or searched, deadlines, when information has been received" and identify "gaps, additional potential sources".
- **Loop**: develop requirements → plan → task → **evaluate reporting** (correlate each report to its SOR; fully satisfied → relieve the asset; partial → annotate "what remains"; **"nothing significant" handled carefully — negative result vs no coverage**) → **update plan** (drop satisfied/overtaken SORs, redirect capacity, re-time LTIOVs). Levers: cueing, redundancy, mix, integration. RFI lifecycle: first check holdings; only when "neither available nor extractable" is a gap declared. Hulnick's critique: collection and analysis run in parallel, not a cycle.

## 7. Genealogy and the Genealogical Proof Standard
GPS = five elements, not a score: reasonably exhaustive research · complete citations · analysis and correlation · resolution of conflicts · written conclusion ([BCG](https://bcgcertification.org/ethics-standards/)). Standard 10: a research question = unique subject identifiers + what is sought. **"Reasonably exhaustive" is an explicit stopping rule**: question answered; sources a competent researcher would examine covered; ≥ 2 independent sources agree; ≥ 1 original with primary information; conflicts resolved; low risk an undiscovered source would overturn — and when thin, widen to **Friends / Associates / Neighbours** ([FAN](https://www.evidenceexplained.com/content/quicklesson-11-identity-problems-fan-principle)).
- **Evidence taxonomy** (Mills) — three orthogonal axes per information item: source *original / derivative / authored*; information *primary / secondary / undetermined*; evidence *direct / indirect / **negative*** ("the dog not barking" — distinct from a failed search). GEDCOM's single `QUAY 0–3` collapses these; Gramps: per-citation confidence 0–4 and **To-Do notes attachable to any object — the task lives on the object with the gap**; Evidentia: Source → Claims (primary/secondary) → Subject+fact → Proof Report with a summary of which claim types were analysed to judge exhaustiveness.
- **Research log** columns: objective, repository/URL, citation *written before searching*, scope ("did nil mean no Fraziers, none named William, or no Williams aged 35–45?"), result. Mills' report skeleton: "full citations for negative results too" and a *revised work plan*.
- **Why hints are dangerous**: Ancestry hints draw on the most-viewed ~10% of collections, are released to reward activity, and tree-to-tree hints "multiply errors across the community". Structurally: a hint is an **unlogged, unscoped, unclassified assertion that bypasses question → plan → scope → nil-logging, and copies a conclusion without its evidence.** Genealogy is the only field with a formal stopping rule and a formal treatment of absence.

## 8. Hypothesis-driven software
ACH: enumerate hypotheses, list evidence, rate consistency per cell, score by *inconsistencies*, sensitivity-test the diagnostic items. **The evaluations are bad**: ACH-trained analysts "did not follow all of the steps" and sometimes got *more* inconsistent (Dhami 2019); "no advantage over no-technique control" (Karvetski & Mandel 2020); "the meaning of consistency is left up to the analyst" (Mandel & Tetlock); "little to no overall benefit, and may even harm" (Wilcox 2023). **What did work**: a short natural-frequency-tree tutorial (54% → 83% coherent judgments), post-hoc coherentisation + aggregation (~61% error reduction), Bayesian-network reformulations. SWARM (IARPA CREATE): analysts reason in "micro-narratives" woven into macro-narratives — tools must let stories and matrices coexist. Boards (Obsidian Canvas, Scrivener corkboard, Aeon Timeline): modest memory/spatial gains; failure mode is apophenia — "string makes every link look equal".

## 9. Alerting and monitoring
Converged model: **Rule** {id, status, scope, query, threshold, false-positive notes, owner, expiry} → evaluated live/scheduled → **Hit** deduplicated by *target* → **Alert/Case** {Unconfirmed → In progress → Confirmed/Dismissed, assignee, comments, activity log, similar cases} → optional promotion to an investigation. Sigma is the portable schema; Sentinel bundles alerts, entities, bookmarks, tasks; Palantir batches and auto-mutes; Linkurious hourly; Maltego `onTimer`. Cost is real: SOCs see ~4,484 alerts/day, 67% unhandled, 83% false positive (Vectra 2023). **Doctrine's version — indicators tied to a warning problem, activated as a "watch condition", deactivated when the threat subsides — is the only one where the alert knows which question it serves.**

## Synthesis

**The common object model.** Entities (typed, aliases) · Links (typed, directed, multiplicity, grade) · Events (time-bounded, theme lines) · Documents/Evidence (captured, hashed, cited, every mention indexed back — "no record stands alone") · Tasks/Actions (MIRSAP state machine; Gramps To-Dos on the gapped object) · Requirements (PIR → indicator → SOR with LTIOV) · Hypotheses (ACH matrix; TIE categories with elimination codes) · Alerts (rule → target-deduped case with triage) · Provenance (SpiderFoot `sourceEventHash`, Palantir lineage, Hunchly hashes) · Gradings (3x5x2 per assertion; Mills' three axes; Admiralty) · Decision log (the SIO Policy File) · Research log with scoped nulls. **No single system has all of them.** Palantir: entities/links/events/provenance/alerts, no tasks/hypotheses/gradings. HOLMES: tasks, hypotheses (TIE), gradings, decision log, provenance — all manual, no expansion. Maltego: expansion with no tasks or provenance-of-reasoning. Genealogy: logs and stopping rules with no graph engine.

**The common control loop.** Information arrives → registered with provenance → read; mentions extracted and indexed/resolved → gaps and lines of enquiry raised as Actions/SORs with priority and deadline → allocated to a collector (human, transform, source) → result returned and *graded* → linked back; hypotheses updated (eliminate/implicate) → new Actions → periodic review of outstanding, referred, pended → repeat until a stopping rule holds.

**What is missing from all of them.**
1. *Nobody models the question.* Palantir, i2, Maltego expand from an entity; only doctrine and GPS start from a requirement, and neither has software.
2. *Absence is not a first-class object.* Only genealogy logs scoped nulls and distinguishes negative evidence from a failed search.
3. *Resolution is brittle (primary keys) or human (Indexers)*; ICIJ's `probably_same_officer_as` edges are the only honest representation of uncertain identity.
4. *Expansion has no budget or objective.* "Run all transforms" exists; "what would change my mind" does not.
5. *Alerts don't know what they serve.*
6. *Tasks are disconnected from the graph* — HOLMES Actions cite an originating document, not a gap on a nominal.
7. *Hypothesis tooling is empirically weak* — wins came from structuring evidence and coherence-checking, not matrices.
8. *No stopping rule anywhere but GPS.*
9. *Provenance covers data, never reasoning* — no system records why a link was drawn or a hint accepted.

## What the Tony Stark version would do differently
**JARVIS is not a bigger link chart. It is HOLMES's Major Incident Room staffed by software, driven by a collection plan, disciplined by the Genealogical Proof Standard.**

**Workflow objects the engine must have**
1. **Question** (PIR-style): subject identifiers + what is sought + why + LTIOV + owner; decomposes into **Indicators** (observables whose presence/absence discriminates) and **Requirements** (indicator × source × scope). *Every other object points at a Question.*
2. **Entity / Link / Event** with typed links carrying multiplicity, direction, and a per-assertion **Grade** (source reliability × information credibility × evidence class direct/indirect/negative — Mills, not QUAY).
3. **Claim**: an atomic assertion extracted from a Document, tagged with its evidence class; identity is a *claim* (`probably_same_as`, with evidence) until promoted to a merge; merges reversible.
4. **Document/Capture**: hash, timestamp, URL, full render, every mention indexed (Hunchly + the Indexer role, automated).
5. **Search record** (research-log row): source, query, scope, timestamp, result *including the scoped null*. Absence becomes queryable.
6. **Action** with the MIRSAP state machine (For Allocation → Allocated → Completed → Resulted → Filed; Referred; Pended), priority tied to a line of enquiry, originating gap and originating document, deadline; automated collectors *recommend*, never self-generate.
7. **Hypothesis / TIE category**: subject sets with provisional elimination codes and the diagnostic evidence for each; scored by inconsistency and coherence-checked (Bayesian, not matrix theatre).
8. **Watch**: a standing query bound to a Question and an Indicator, with expiry, target-dedup, batching, auto-mute — never a free-floating rule.
9. **Decision log**: the SIO Policy File — numbered, timestamped, immutable rationale for scope, elimination criteria, referrals.
10. **Expansion budget**: Maltego's slider and `userFilter()` generalised — each Action has a cost, each Question a budget, and expansion must justify itself against an Indicator.

**Loops the engine must run**
- **Ingest loop** (Receiver/Reader/Indexer): capture → extract claims → resolve as claims → index every mention → raise Actions where a line of enquiry is apparent → priority.
- **Gap loop** (Action Manager + Collection Manager): for each open Question, compute which indicators lack evidence, which entities lack expected properties (FAN-style: known associates unsearched), which searches are stale; emit Actions with LTIOV; reprioritise continually; refer low-value ones explicitly rather than let them rot.
- **Evaluate-returns loop**: every result tagged to the Action/SOR it satisfies; partial → "what remains"; "nothing significant" distinguished from "no coverage"; grade attached; hypothesis scores updated; a return that changes the plan triggers re-tasking (cueing).
- **Review loop**: periodic sweep of outstanding, referred, pended Actions and stale Watches; Key Assumptions Check on the Question itself.
- **Stopping rule**: a Question closes only when GPS-style criteria hold — independent sources agree, conflicts resolved, absence searched and logged, low risk an unexplored source overturns it — and the closure is written as a proof argument with citations, not a chart.

**The gap between "link chart software" and "a system that investigates" is exactly the gap between Palantir and MIRSAP: one has the graph, the other has the loop. Build the loop, then give it the graph.**
